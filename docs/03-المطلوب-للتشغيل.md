# LIONX — المطلوب للتشغيل الفعلي

## الفرق بين المعاينة والتشغيل التجاري

الموقع الحالي يعمل كواجهة ومول MVP مع دفع يدوي للمراجعة. التشغيل التجاري يعني أن الطلبات والأرصدة والإيصالات والصلاحيات تصبح بيانات موثوقة محفوظة على خادم، وأن كل عملية مالية يمكن تتبعها وإيقافها أو عكسها وفق سياسة واضحة. لا ينبغي اعتبار الموقع نظام دفع إنتاجيًا قبل إكمال البنود التالية.

## المتطلبات الحرجة

| الأولوية | المطلوب | سبب الحاجة | النتيجة عند التنفيذ |
|---|---|---|---|
| حرجة | اختيار مزود دفع معتمد وإتمام KYC التجاري | قبول مدفوعات حقيقية بطريقة قانونية وتشغيلية | بيئة Sandbox ثم Production |
| حرجة | Backend آمن وقاعدة بيانات | منع الاعتماد على الحالة المحلية وحماية الطلبات والأرصدة | سجل مركزي للطلبات والعمليات |
| حرجة | تخزين آمن للإيصالات | استقبال الصور وPDF ومراجعتها دون تركها داخل الجهاز | Object Storage خاص وروابط مؤقتة |
| حرجة | Webhooks موثقة ومتحقق من توقيعها | معرفة نتيجة الدفع من المصدر وليس من المتصفح | تحديث موثوق لحالة العملية |
| عالية | مصادقة المستخدمين والجلسات | ربط الطلبات والمحفظة بالحساب عبر الأجهزة | حسابات حقيقية واسترجاع آمن |
| عالية | Admin RBAC و2FA | منع أي موظف أو مستخدم من تغيير بيانات حساسة بلا صلاحية | أدوار وسجل تدقيق وموافقات |
| عالية | محرك التسعير | توحيد تكلفة المورد والربح والرسوم والضريبة | سعر محفوظ عند إنشاء الطلب |
| عالية | تكامل مورد موثق | جلب تكلفة وتوفر وتسليم حقيقي | كتالوج إنتاجي بدل البيانات التجريبية |
| متوسطة | سياسات الاسترداد والإلغاء | حماية العميل والفريق في حالات الفشل | حالات تشغيلية قابلة للتطبيق |
| متوسطة | تنبيهات ومراقبة | اكتشاف Webhook فاشل أو عملية معلقة | إشعارات وسجل أخطاء |
| متوسطة | نطاق مخصص وAnalytics | تحسين الوصول وقياس التحويل | موقع تجاري قابل للقياس |

## الدفع اليدوي الحالي وما يحتاجه

صفحة `/payment-methods` تعرض أرقام محافظ LIONX وتسمح بنسخها، ثم تجمع رقم محفظة العميل وإثبات الدفع. لكي تصبح هذه العملية إنتاجية، يجب إرسال البيانات إلى Backend عبر اتصال آمن، حفظ الإثبات في Storage خاص، منع تكرار رقم الإثبات أو الطلب، وإضافة شاشة Admin للمراجعة. لا تتم إضافة الرصيد إلا بعد أن يوافق موظف مخول، ويجب تسجيل اسم المراجع ووقت القرار وسبب الرفض عند الحاجة.

## LionxPay الفعلي

صفحة `/pay/cards` تحتاج عقدًا واضحًا بين الواجهة والخادم: إنشاء Payment Intent، عرض رابط الدفع أو client secret قصير العمر، ثم انتظار Webhook. صفحة `/pay/charge` تحتاج إنشاء طلب شحن رصيد لا يغيّر الرصيد قبل التأكيد. صفحة `/pay/withdraw` تحتاج RBAC ومراجعة يدوية وحدودًا وسجلًا ماليًا. صفحة `/pay/kyc` تحتاج مزود تحقق أو تخزينًا مشفرًا وسياسة حذف واحتفاظ.

لا توضع مفاتيح API أو أسرار Webhook داخل `app/` أو JavaScript الخاص بالويب. تحفظ الأسرار في Secret Manager أو متغيرات بيئة خادمية، وتُراجع السجلات لمنع ظهورها.

## ما يجب اعتماده من صاحب المشروع

| القرار | ما يجب تحديده |
|---|---|
| نموذج الحساب | تسجيل برقم الهاتف، بريد إلكتروني، أو مزود هوية خارجي |
| العملة | الجنيه المصري فقط أم عملات أخرى |
| الدفع | البطاقات، المحافظ، InstaPay، أم مزود محدد |
| الشحن والسحب | هل الشحن متاح؟ هل السحب متاح؟ ومن يوافق عليه؟ |
| المورد | هل Gamsgo هو المورد المعتمد؟ وما الخدمات والـAPI المسموح بها؟ |
| التسعير | قيمة markup والرسوم والضريبة وقواعد التقريب |
| التشغيل | من يراجع الإيصالات؟ ما زمن الاستجابة؟ وما سياسة الرفض والاسترداد؟ |
| البيانات | مدة الاحتفاظ بالإيصالات وبيانات KYC ومن يحق له رؤيتها |
| النطاق | هل سيبقى GitHub Pages أم سيتم ربط نطاق تجاري مخصص؟ |

## ترتيب التنفيذ المقترح

يبدأ العمل بتثبيت المتطلبات واختيار مزود الدفع، ثم Backend وقاعدة البيانات، ثم Storage للإيصالات، ثم الحسابات وRBAC، ثم محرك التسعير وتكامل المورد، ثم Sandbox واختبارات Webhooks. بعد نجاح التشغيل الداخلي فقط يُفعّل الإنتاج تدريجيًا.

## تعريف الجاهزية

لا تعتبر LIONX جاهزًا للتشغيل التجاري إلا عندما يمكن إنشاء طلب بحساب حقيقي، حساب سعر قابل للتفسير، استقبال دفع أو إثبات بشكل آمن، تأكيد العملية من الخادم أو من مراجع مخول، تحديث الرصيد مرة واحدة فقط، وإظهار حالة يمكن تدقيقها من المستخدم والفريق. حتى ذلك الوقت، تبقى النسخة الحالية **جاهزة للمعاينة وMVP اليدوي، وليست قاعدة مالية إنتاجية**.
