# LIONX — علاقات الأقسام والتدفقات

## الصورة العامة

يتكون LIONX من خمسة قطاعات رئيسية في المول: **PLAY** للألعاب والشحن، **PAY** للدفع والبطاقات والمحافظ، **GROW** للنمو والتسويق، **DIGITAL** للاشتراكات والأدوات، و**VIP** للخدمات الخاصة. هذه القطاعات ليست مواقع منفصلة؛ كلها تعتمد على كتالوج الخدمات المشترك، وتستخدم نفس بطاقات الخدمة والسلة والهوية والتنقل.

## علاقة الأقسام ببعضها

| من | إلى | العلاقة |
|---|---|---|
| الصفحة الرئيسية | القطاعات الخمسة | نقطة اكتشاف واختيار المسار |
| القطاعات | المتجر | تعرض مجموعة الخدمات المناسبة لكل هدف |
| المتجر | تفاصيل الخدمة | كل بطاقة خدمة تفتح وصفًا وسعرًا ووقت تسليم وإجراء إضافة للسلة |
| تفاصيل الخدمة | السلة | إضافة الخدمة مع حفظها في الحالة المحلية |
| السلة | Checkout | مراجعة العناصر والإجمالي قبل الإرسال |
| Checkout | الدفع اليدوي | دفع إجمالي الطلب أو التحول إلى شحن الرصيد |
| المحفظة | شحن الرصيد | زر إضافة رصيد يفتح نفس نموذج الدفع اليدوي بنوع `wallet_topup` |
| الدفع اليدوي | الطلبات | إنشاء عملية بحالة `pending_review` بعد إدخال المحفظة والإيصال |
| الطلبات | التتبع | عرض الحالة وسجل الأحداث المحلي |
| الطلبات | WhatsApp | التواصل اليدوي باستخدام رقم الطلب للمطابقة |
| الشركات | Quote Builder | تحويل احتياج الشركة إلى طلب نطاق وعرض سعر |
| المحتوى | القطاعات والخدمات | يشرح الاستخدام ويساعد على اختيار المسار، لكنه لا يغير الأسعار |
| الإدارة | الكتالوج والطلبات | في المستقبل فقط؛ حاليًا صفحات تمهيدية بلا صلاحيات فعلية |
| LionxPay | الدفع والإدارة | في المستقبل فقط؛ لا يغير الرصيد ولا ينفذ سحبًا في النسخة الحالية |

## تدفق العميل الفردي

يصل العميل إلى الصفحة الرئيسية، يختار قطاعًا أو يبحث عن خدمة، ثم يفتح تفاصيل الخدمة ويضيفها إلى السلة. عند Checkout يرى إجمالي الطلب ويستطيع الانتقال إلى `/payment-methods`. هناك يختار **دفع قيمة الطلب**، يختار طريقة التحويل، ينسخ رقم محفظة LIONX، يكتب رقم محفظته، ويرفع الإثبات. بعد الإرسال يحصل على رقم طلب وحالة مراجعة، ويمكنه استخدام التتبع أو واتساب.

## تدفق شحن الرصيد

من صفحة `/wallet` يضغط العميل **إضافة رصيد**. ينتقل إلى `/payment-methods?operation=wallet_topup`، يحدد مبلغًا ضمن الحدود، يختار Vodafone Cash أو Orange Money أو InstaPay، ثم يرسل رقم المحفظة والإثبات. العملية تُسجل للمراجعة، لكن قيمة الرصيد لا تتغير آليًا. مستقبلًا تمر العملية عبر Admin RBAC، وبعد الموافقة فقط يُسجل قيد مالي في دفتر حركات مركزي.

## تدفق الشركات

ينتقل العميل التجاري من الصفحة الرئيسية أو Corporate إلى Quote Builder، يحدد اسم الشركة والخدمات والتفاصيل، ثم يرسل طلب نطاق مبدئي. هذا التدفق منفصل عن دفع B2C؛ فهو لا يمنح ائتمانًا ولا ينشئ سعرًا نهائيًا قبل المراجعة. في المرحلة الإنتاجية يصل الطلب إلى فريق المبيعات أو لوحة Admin، ثم يُنشأ عرض سعر معتمد.

## التدفق المستقبلي لـLionxPay

| الصفحة | المدخل | الخادم المستقبلي | القرار |
|---|---|---|---|
| `/pay/cards` | بيانات عملية أو رابط دفع | Payment Intent ومزود بطاقات | ينتظر Webhook |
| `/pay/charge` | مبلغ شحن | عملية شحن معلقة | لا يتغير الرصيد قبل التأكيد |
| `/pay/withdraw` | مبلغ السحب ووجهته | طلب سحب ومراجعة RBAC | موافقة يدوية وسجل تدقيق |
| `/pay/kyc` | بيانات التحقق | مزود KYC أو Storage مشفر | سياسة احتفاظ وحذف |

## حدود الثقة بين الأقسام

الكتالوج يصف الخدمة ولا يثبت الدفع. السلة تحسب إجماليًا للعرض ولا تمثل دفترًا ماليًا. صفحة الدفع تجمع بيانات التحويل ولا تعتبرها ناجحة. شاشة نجاح الطلب تؤكد استلام طلب المراجعة فقط. الإدارة المستقبلية هي التي توافق على الإثبات، ومحرك التسعير هو الذي يثبت السعر، والخادم هو الذي يحدد النتيجة النهائية.

## حالات البيانات

| الكيان | الحالات أو البيانات الأساسية |
|---|---|
| الخدمة | معرف، اسم، قطاع، سعر عرض، وصف، زمن تسليم |
| السلة | عناصر، كميات، إجمالي مشتق |
| الطلب | رقم، عناصر، مبلغ، حالة، سجل أحداث |
| الدفع اليدوي | الطريقة، رقم محفظة العميل، اسم الإثبات، `pending_review` |
| المحفظة | رصيد تجريبي حالي، عمليات محلية، لا تمثل أموالًا حقيقية |
| عرض الشركات | اسم الشركة، الخدمات، التفاصيل، حالة مراجعة |
| الإدارة | صفحات تمهيدية فقط حتى اعتماد RBAC |

هذا الفصل بين المسؤوليات يمنع أن تقوم صفحة واجهة بتغيير رصيد أو إعلان نجاح مالي. وهو أساس الانتقال الآمن من MVP محلي إلى نظام تشغيل خادمي.
